# ChatGPT ↔ локальный ПК: протокол снапшотов и патчей

Версия: 0.1 · Проверено: 2026-10-08 · Репозиторий-посредник: `AlexPastukhh/test`.

> Это инструкция для **других чатов ChatGPT**. Сначала прочитай этот файл целиком. Не полагайся на память другого чата, его `file_id` или временные ссылки.

## 1. Цель

Получать один снимок **рабочей папки репозитория на Windows**, включая выбранные незакоммиченные и неотслеживаемые файлы; скачивать его как **реальный файл текущего чата** через GitHub Actions Artifact; распаковывать и редактировать **в среде ChatGPT**; формировать патч и **одной командой туннеля** применять его на ПК. Целевой бюджет: два логических обращения к ПК на штатный цикл (публикация снимка, применение патча). Диагностика и сбои могут добавить обращения.

```text
Windows repo --(ПК-туннель: snapshot + git push)--> GitHub repo
GitHub Actions --(artifact ZIP; GitHub plugin)--> ChatGPT file_id / filesystem
ChatGPT: unzip -> edit/test -> changes.patch
ChatGPT --(ПК-туннель: verify + git apply)--> Windows repo
```

## 3. Инструменты и ограничения

| Инструмент | Для чего | Ограничения |
|---|---|---|
| Windows-туннель (`start_process`, `write_file`) | PowerShell и работа с локальными файлами | Сессия может разорваться; пути/команды могут блокироваться |
| GitHub `fetch` / `fetch_file` | Чтение репо и текста | `fetch` не скачивает бинарные ZIP как вложения |
| GitHub `fetch_workflow_run_artifacts` | Найти Artifact для нужного run | ID изменяются |
| GitHub `download_workflow_artifact` | Доставить ZIP в файловую систему текущего чата | Возвращает connector `file_id` |
| Git / `git apply` на ПК | Проверить и применить патч | Не создаёт commit автоматически |

## 5. Публикация и получение снапшота

1. Уточни путь **конкретного проекта на Windows**, если он не указан. Не сканируй другие проекты без запроса.
2. Через туннель проверь путь, `git -C <path> remote -v`, `git status --short`, имя ветки и текущий HEAD.
3. **Перед отправкой проверяй состав.** Исключи `.git/`, `snapshots/`, `node_modules/`, кеши, `.env*`, токены/ключи, большие binaries, symlinks за пределы проекта. Учти tracked и подходящие untracked файлы. Git-ignore не исключает уже tracked secrets.
4. Архивируй **локальную рабочую директорию**, а не `git archive HEAD` и не `actions/checkout`. Сохраняй именно согласованные локальные изменения.
5. Для тестового посредника положи готовый архив по пути `snapshots/local-snapshot.zip`; проверь открытие и список файлов ZIP.
6. Коммить **только** `snapshots/local-snapshot.zip` и отправь в GitHub. Не делай `git add -A`: иначе коммит затронет локальные изменения проекта. Не смешивай test files с документацией.
7. Через GitHub-плагин найди run на нужном `head_sha`. Предпочитай `status=completed, conclusion=success`; найди `chatgpt-snapshot` через `fetch_workflow_run_artifacts`.
8. Скачай Artifact через `download_workflow_artifact` с **актуальным ID**, убедись, что ZIP действительно доступен в файлах текущего чата. Распакуй внешний и внутренний ZIP.
9. Работай автономно с копией исходника в ChatGPT. При недоступных компиляторах/зависимостях обозначай, какие тесты не выполнены, а не вызывай ПК для каждой операции.

## 6. Обратная передача патча на ПК

1. Сохрани baseline исходного ZIP неизменённым, редактируй отдельную копию.
2. Создай **единый Git-compatible patch** между baseline и изменёнными файлами. Например, используй временный репозиторий: `git init`, `git add -A`, `git commit -m baseline`, затем изменения, `git add -A`, `git diff --cached --binary HEAD > changes.patch`.
3. Составь манифест: Windows-путь, ID/хеш снапшота, список затрагиваемых файлов, исходные SHA-256 (на байтах Windows), SHA-256 патча.
4. В **одном вызове** Windows `start_process` для небольшого патча: безопасно передай содержимое (например, Base64); запиши временный `.patch`; проверь SHA-256; сравни исходные хеши на ПК; `git apply --check`; `git apply`; затем проверь изменённые файлы. **При несовпадении остановись**.
5. Для небольших патчей **GitHub обратно не нужен**. У туннеля нет метода, который принимает `file_id` ChatGPT и автоматически копирует двоичный файл, зато PowerShell принимает данные в аргументах и умеет записывать файлы.
6. Для больших патчей, бинарных файлов и ограничений на размер аргументов нужен отдельно согласованный транспорт, например временный **приватный** GitHub-посредник с проверкой SHA.
7. В Windows `core.autocrlf=true` может менять LF/CRLF: после применения отличай побайтовый SHA-256 от содержательного совпадения. Не помечай несовпавший SHA как успех.
8. `git apply` меняет рабочую директорию и **не создаёт коммит**. Без явного запроса не делай `commit`, `push`, `reset --hard`, `clean -fdx` или перезапись конфликтующих файлов.

## 7. Проблемы и проверки

- `Session terminated` / `MCP server is not initialized`: перепроверь подключение и завершение предыдущей команды. Оборванный ответ не доказывает, что команда не выполнилась.
- Запись через GitHub-плагин требует approval: при отказе не повторяй тот же путь. Можно воспользоваться согласованным пользователем `git/gh` на ПК.
- Run ещё выполняется: проверяй нужный SHA и run; не используй устаревший Artifact.
- GitHub Artifact отдаёт **ZIP, содержащий твой ZIP**: распакуй два слоя.
- `git apply --check` не прошёл: патч/версия/путь/строки не совпадают. Не форсируй.
- Разошлись хеши после патча: проверь BOM, CRLF/LF, кодировку; зафиксируй причину, не называй побайтовым совпадением.
- Снапшот содержит секреты или чувствительные данные, а посредник PUBLIC: **СТОП**, не публикуй; нужен приватный канал.

## 8. Правила для нового чата

- Сначала прочитай **этот документ** из GitHub; открой также `CHATGPT_START_HERE.md`.
- Не рассчитывай, что `file_id`/архив прошлого чата доступен в новом.
- Разделяй `обнаружен`, `получен`, `распакован`, `проверен`, `применён`; не заявляй о завершении без проверки.
- Сохраняй исходные локальные правки, не коммить их без запроса. Не публикуй private data в публичный репозиторий.
- Минимизируй вызовы ПК: один для свежего снапшота и один для применения патча при нормальной работе; GitHub и обработка в ChatGPT — между ними.
- Если пользователь просит только читать репозиторий, не применяй патчи.

При подтверждённых изменениях процесса обновляй дату, версию, результат теста и известные ограничения. Не представляй предполагаемые функции плагинов как проверенные. До использования для других проектов нужно отдельно реализовать приватный общий репозиторий, многопроектное именование, секрет-сканирование и безопасную публикацию.
